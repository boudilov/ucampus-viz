# WebSocket-события визуализации

Документация для фронтенда экрана-визуализации («солнечная система», исходное ТЗ — `ws_events.md`).
Описывает то, что бэкенд отдаёт **сейчас**, а не планируемое.

Готовая заготовка с подключением и заглушками обработчиков: `public/ws-starter.html`
(открывается по адресу `/ws-starter.html`). Проверить, что события реально идут:
страница `/ws-showcase` — счётчики по типам событий.

## Транспорт

WebSocket-сервер — [sockudo](https://github.com/sockudo/sockudo), совместим с протоколом Pusher.
Поэтому подходят любые Pusher-клиенты: `laravel-echo` + `pusher-js`, чистый `pusher-js`
или нативный `WebSocket`.

Канал **`visualization`**, публичный: авторизация и `/broadcasting/auth` не нужны.

### Параметры подключения

Не хардкодьте — забирайте с эндпоинта:

```http
GET /visualization/config
```

```json
{
  "key": "uu-visualization-key",
  "host": "",
  "port": 6001,
  "scheme": "http",
  "channel": "visualization",
  "heartbeat_interval": 30,
  "timeout_seconds": 90,
  "snapshot_url": "http://uu.local:7072/visualization/snapshot"
}
```

Пустой `host` означает «тот же хост, что и у приложения» — подставляйте `location.hostname`.
`key` публичный по устройству протокола; секрет приложения на клиент не отдаётся никогда.

### Подключение через Laravel Echo

```js
const config = await fetch('/visualization/config').then((r) => r.json())

window.Echo = new Echo({
    broadcaster: 'pusher',
    key: config.key,
    wsHost: config.host || window.location.hostname,
    wsPort: config.port,
    wssPort: config.port,
    forceTLS: config.scheme === 'https',
    disableStats: true,
    enabledTransports: ['ws', 'wss'],
    cluster: 'mt1', // требуется pusher-js, self-hosted сервером игнорируется
})

Echo.channel(config.channel)
    .listen('.user.appeared', (envelope) => { /* ... */ })
```

**Точка перед именем события обязательна.** Имена задаются сервером через `broadcastAs()`,
и без ведущей точки Echo подставит неймспейс `App\Events\` и обработчик не вызовется.

### Подключение без Echo

```js
const ws = new WebSocket(`ws://${host}:${port}/app/${key}?protocol=7&client=js&version=8.4.0`)

ws.addEventListener('message', (message) => {
    const frame = JSON.parse(message.data)

    // Сервер проверяет живость соединения и рвёт его через ~120 секунд без ответа
    if (frame.event === 'pusher:ping') {
        ws.send(JSON.stringify({ event: 'pusher:pong', data: {} }))
        return
    }

    if (frame.event === 'pusher:connection_established') {
        ws.send(JSON.stringify({ event: 'pusher:subscribe', data: { channel: 'visualization' } }))
        return
    }

    if (frame.channel === 'visualization') {
        const envelope = JSON.parse(frame.data) // конверт приходит строкой
    }
})
```

## Формат сообщения

Все события — единый конверт:

```json
{
  "event": "user.booking.created",
  "timestamp": "2026-08-28T12:41:04Z",
  "session_id": "55555555-5555-4555-8555-555555555555",
  "payload": { "...": "зависит от события" }
}
```

| Поле | Тип | Описание |
|---|---|---|
| `event` | string | Тип события, совпадает с именем в `listen()` |
| `timestamp` | string | ISO-8601, UTC, секундная точность. **Порядок анимаций стройте по нему, а не по порядку прихода** |
| `session_id` | string (uuid) | Идентификатор вкладки. **Одна звезда = один `session_id`** |
| `payload` | object | Данные события |

Про идентификаторы:

- `session_id` — вкладка, а не пользователь. Один человек с двумя открытыми вкладками — две
  независимые звезды. Живёт до закрытия вкладки, переживает переходы по страницам сайта.
- `payload.user_id` — **анонимный хеш** (12 hex-символов), не id из базы. Годится, чтобы
  сгруппировать вкладки одного человека или посчитать уникальных, но не для показа личности.
  У неавторизованных гостей — строка `guest`.

## События

Все `payload` содержат общий блок:

| Поле | Тип | Описание |
|---|---|---|
| `user_id` | string | Анонимный хеш пользователя, у гостей `guest` |
| `user_role` | string | `student`, `teacher`, `administrator`, `coordinator`, `guest` |
| `user_course` | string \| null | Поток студента, например `2-й курс`. У сотрудников и гостей `null` |

### `user.appeared` — зашёл на сайт

Звезда появляется в открытом космосе. Дополнительных полей нет.

### `user.schedule.opened` — открыл расписание РЦ

Звезда выходит на орбиту мастерской. Дополнительно: `workshop_id` (int).

Приходит при открытии расписания, недельного и месячного вида, списков и формы бронирования.

**Переход между мастерскими промежуточного `closed` не даёт**: при уходе из расписания РЦ 4
сразу в расписание РЦ 6 придёт только новый `opened` с `workshop_id: 6` — переводите звезду
между орбитами напрямую.

Повторные heartbeat на той же странице события **не порождают** — оно приходит только на смену
состояния.

### `user.schedule.closed` — ушёл из расписания без брони

Звезда возвращается в открытый космос. Дополнительно: `workshop_id` (int) — орбита, которую покинул.

### `user.booking.created` — бронь создана

Полёт в центр со вспышкой. Дополнительно: `workshop_id` (int), `booking_id` (int).

Что происходит дальше: сервер держит сессию в состоянии `booked`, а на следующем heartbeat
переводит её в `drifting` или `orbiting` — в зависимости от того, где пользователь оказался
после редиректа (обычно он попадает обратно в расписание, то есть на орбиту, и это будет
`user.schedule.opened`). **Отдельного события «вспышка закончилась» нет** — сколько звезда
светится в центре, решает фронт по своему таймеру.

### `user.booking.blocked` — бронь не удалась

Дополнительно: `workshop_id` (int), `reason` (string).

**Состояние звезды не меняется** — она остаётся на орбите. Событие для подсветки трения.

`reason`: `slot_taken` (ресурс занят в выбранное время), `no_induction` (не пройден инструктаж),
`no_photo` (нет фото), `other` (всё остальное — санкции, ограничения по времени, незаполненные
обязательные группы ресурсов). На практике сейчас приходят преимущественно `slot_taken` и `other`.

### `user.exit` — ушёл с сайта

Звезда гаснет. Дополнительных полей нет.

Приходит в двух случаях: вкладка закрыта (браузер успел отправить сигнал) либо от неё не было
heartbeat дольше таймаута — тогда событие генерирует сервер в течение минуты.

## Снапшот состояния

Событий в сокете достаточно, только пока экран открыт. При запуске и **при каждом
переподключении** запрашивайте текущую картину:

```http
GET /visualization/snapshot
```

```json
{
  "event": "state.snapshot",
  "timestamp": "2026-08-28T08:48:16Z",
  "session_id": null,
  "payload": {
    "sessions": [
      {
        "session_id": "48d4a411-533e-455b-a044-fc8d33bea8ff",
        "user_id": "c21c3e7a6bd7",
        "user_role": "administrator",
        "user_course": null,
        "state": "orbiting",
        "workshop_id": 6
      }
    ]
  }
}
```

`state`: `drifting` (в открытом космосе), `orbiting` (на орбите `workshop_id`),
`booked` (только что создал бронь). Отдаются только живые сессии — те, от которых heartbeat
приходил не позже `timeout_seconds` назад.

Снапшот — это состояние, а не история: событий, которые прошли до подключения, в нём нет,
есть только их результат.

## Справочник мастерских

В событиях приходит только `workshop_id`. Названия и цвета орбит — здесь:

```http
GET /visualization/workshops
```

```json
{
  "workshops": [
    {
      "id": 15,
      "name": "Центр Информационных Ресурсов",
      "name_en": "Learning Resource Centre",
      "slug": "learning-resource-centre",
      "position": 10,
      "color": "#cb51d6",
      "cover_url": "https://ucampus.u.university/storage/workshop-15/cover.jpg?1712345678"
    }
  ]
}
```

| Поле | Тип | Описание |
|---|---|---|
| `id` | int | Совпадает с `workshop_id` в событиях |
| `name`, `name_en` | string \| null | Названия. Английское заполнено не у всех |
| `slug` | string \| null | Читаемый идентификатор, например `ceramics-workshop` |
| `position` | int \| null | Порядок показа в кабинете; список уже отсортирован по нему, мастерские без `position` в конце |
| `color` | string | HEX-цвет орбиты |
| `cover_url` | string \| null | Обложка мастерской, `null` если файла нет |

Про `color`: своего цвета у мастерских в базе нет, поэтому бэкенд вычисляет его по золотому углу
от порядкового номера — соседние орбиты гарантированно различимы, цвет стабилен между запросами,
и новая мастерская не перекрашивает существующие. Если для экрана нужна своя палитра —
используйте `id` или `slug` как ключ и игнорируйте это поле.

Список запрашивается один раз при старте: мастерские меняются редко. Учтите, что среди них есть
служебные вроде «Тест РЦ» — фильтровать их по своему усмотрению.

## Жизненный цикл звезды

```
                    user.appeared
                          │
                          ▼
                    ┌──────────┐   user.schedule.opened   ┌──────────┐
                    │ drifting │ ───────────────────────► │ orbiting │ ◄─┐
                    └──────────┘ ◄─────────────────────── └──────────┘   │ user.schedule.opened
                          ▲       user.schedule.closed          │        │ (другой workshop_id)
                          │                                     │        │
                          │                user.booking.created │        │
                          │                                     ▼        │
                          │  следующий heartbeat          ┌──────────┐   │
                          └────────────────────────────── │  booked  │ ──┘
                                                          └──────────┘
                    user.exit — из любого состояния, звезда гаснет
                    user.booking.blocked — состояние не меняется
```

## Что гарантировано, а что нет

- **Доставка не гарантирована.** События не буферизуются: всё, что прошло во время обрыва
  соединения, потеряно. Лечится перезапросом снапшота при каждом `connected`.
- **Порядок прихода не гарантирован.** Ориентируйтесь на `timestamp`. Учтите: он с точностью
  до секунды, поэтому несколько событий одной сессии могут иметь одинаковое значение —
  для них сохраняйте порядок получения.
- **Дубликаты возможны** при повторной отправке одного действия. Обработчики должны быть
  идемпотентны: `opened` для орбиты, где звезда уже находится, не должен ломать анимацию.
- `session_id` может прийти в `opened`/`created` без предшествующего `appeared` — например,
  если экран подключился в середине сессии пользователя. Создавайте звезду по факту любого
  события с незнакомым `session_id`.
- Задержка: события отправляются синхронно в момент действия пользователя, типичная задержка
  до экрана — десятки миллисекунд.

## Тайминги

| Параметр | Значение | Что означает для фронта |
|---|---|---|
| `heartbeat_interval` | 30 сек | Как часто вкладка отмечается на сервере |
| `timeout_seconds` | 90 сек | После этого молчания сервер сам шлёт `user.exit` |
| Проверка таймаутов | раз в минуту | `user.exit` по обрыву приходит с задержкой до ~1.5 мин |
| `activity_timeout` сокета | 120 сек | Отвечайте на `pusher:ping`, если работаете без Echo |

## Разработка с localhost

Подключаться можно с любого origin — ни WebSocket, ни HTTP-эндпоинты по умолчанию не ограничены
списком доменов. Отдельный стенд поднимать не нужно: разрабатывайте фронтенд локально,
а события берите с рабочего сервера.

```bash
npm run dev            # например, vite на http://localhost:5173
```

```js
// в коде экрана указывается только адрес кабинета
const API = 'https://ucampus.u.university'

const config = await fetch(`${API}/visualization/config`).then((r) => r.json())
```

Готовый стартер умеет это из коробки — параметр `api`:

```
http://localhost:5173/ws-starter.html?api=https://ucampus.u.university
```

Обратите внимание: `config.host` в проде указывает на публичный домен, поэтому WebSocket
пойдёт на сервер кабинета, даже когда сама страница открыта с `localhost`. Смешивания
протоколов при этом не происходит: страница по `http`, сокет по `wss` — браузер это разрешает.

Если доступ понадобится ограничить, на стороне бэкенда есть две независимые переменные:
`SOCKUDO_ALLOWED_ORIGINS` (кому можно подключаться к сокету) и `VISUALIZATION_CORS_ORIGINS`
(CORS для `/visualization/*`). Пустые значения означают «разрешено всем».

## Чего сейчас нет

- Нет истории событий и агрегатов за день — только текущее состояние.
- Нет отдельного события об окончании вспышки после `user.booking.created`.

## Как проверить работу локально

Сгенерировать события без реальных действий пользователя:

```bash
docker compose exec php php artisan tinker
```

```php
$t = app(App\Services\Visualization\VisualizationTracker::class);
$w = App\Models\Workshop::find(4);
$u = App\Models\User::where('role', 'student')->whereNotNull('uu_data')->first();
$sid = '11111111-1111-4111-8111-111111111111';

$t->sync($sid, $u, 'drifting', null);      // user.appeared
$t->sync($sid, $u, 'orbiting', $w);        // user.schedule.opened
$t->bookingBlocked($sid, $u, $w, 'slot_taken');
$t->bookingCreated($sid, $u, $w, 999);     // user.booking.created
$t->exitBySessionId($sid);                 // user.exit
```
